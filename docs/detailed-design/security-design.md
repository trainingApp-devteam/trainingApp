## 2. 脅威と保護対象

保護対象はパスワード、セッション、招待トークン、トレーニング記録、身体測定、DB認証情報、将来のSpotify OAuthトークン。主な脅威は、他利用者データへの不正アクセス、招待URL漏えい、認証情報の総当たり、XSS/CSRF、秘密情報のGit・ログへの混入、公開DBへの直接接続である。

## 3. 認証

- ログイン識別子は正規化済みユーザー名、資格情報はパスワード。
- パスワードはSpring Securityが提供するBCrypt等の適切な一方向ハッシュで保存する。平文や復号可能な暗号で保存しない。
- パスワード最小長、最大長、漏えい済みパスワード対策は実装時に方針を固定する。不要な複雑性ルールは避ける。
- エラー応答はユーザー名の存在、承認状態、停止状態を外部へ漏らさない。
- ログイン失敗をユーザー名・IP等でレート制限する。利用者ロックを行う場合はAdminによる解除手順を用意する。
- 初期Adminは環境変数または一度限りの初期化処理で作る。既定資格情報をコミットしない。
- パスワードリセットは未決。メールを使わない場合の本人確認とAdmin運用を決めるまで機能を公開しない。

## 4. アカウント状態と権限

- 招待申請で作られた利用者は`PENDING_APPROVAL`であり、認証成功扱いにしない。
- Admin1名のみが招待発行、承認、却下を実行できる。承認済みアカウントの停止機能は初期リリース対象外。
- 一般利用者は自身の記録・メニュー・測定のみ操作可能。
- Adminであっても通常のAPI・画面から他人の健康関連データを参照できない。
- URLのID、hidden input、React側のガードは認可根拠にならない。全APIでサーバー側認可を行う。
- ID指定の所有者不一致は原則404相当で応答し、IDの存在を漏らさない。
- 招待発行・承認・却下の実施者、対象、時刻を記録する。記録内容やトークン値は監査ログに含めない。

## 5. セッション・ブラウザー保護

- 同一オリジン配信とSpring Securityのサーバーセッションを第一案とする。
- セッションCookieに`HttpOnly`, `Secure`, `SameSite=Lax`相当を設定し、本番ではHTTPSを強制する。
- ログイン成功時にセッションIDをローテーションし、ログアウト時にサーバーセッションを失効させる。
- Cookieベース認証ではCSRF保護を有効にする。状態変更APIでCSRFトークンを検証する。
- CORSが必要な場合は許可Originを明示し、ワイルドカードと資格情報付きCookieを併用しない。
- トークン・認証情報を`localStorage`やURLクエリへ保存しない。
- Reactはユーザー入力をHTMLとして無害化せず直接挿入しない。Content Security Policyを公開環境で設定する。

## 6. 招待とアカウント申請

- 招待トークンは暗号学的に強い乱数で生成し、DBにはハッシュのみ保存する。
- トークンを一度だけ使用可能にし、有効期限とAdminによる失効を検証する。
- 招待リンクをアクセスログ、解析イベント、エラーレポートに記録しない。Referer経由の流出も抑える。
- 申請後は招待を使用済みにし、Admin承認まではログイン不可とする。
- 招待をメール送信する場合は、送信サービス、送信先保護、再送・失効手順を別途追加設計する。

## 7. 入力・データ保護

- サーバー側で長さ、範囲、形式、所有者、関連IDを検証する。
- DBアクセスはJPAパラメーター化クエリ等を用い、SQL文字列連結を避ける。
- HTML出力時はコンテキストに応じてエスケープする。
- 消費カロリー値はクライアント入力を信用せず、サーバーが有効な係数とセット値から計算する。
- 音楽再生のYouTube埋め込みは、利用者が「音楽を再生」を押すまで読み込まない（押すまでYouTubeへ通信しない）。埋め込みは`youtube-nocookie.com`を使う。配信サーバーは`Referrer-Policy: no-referrer`だが、YouTubeの埋め込みは参照元が無いと再生できないため、埋め込みのiframeだけ`referrerpolicy="strict-origin-when-cross-origin"`（送るのはオリジンのみ）とする。CSPを導入する場合は`frame-src https://www.youtube-nocookie.com`と`script-src https://www.youtube.com`を許可する。
- IDOR対策として、子レコード操作でも親トレーニング記録の所有者まで検証する。
- 身体情報は必要最小限のみ保存し、公開前にプライバシー告知・保存期間・削除要件を確認する。
- DB接続はプライベートネットワークに限定し、DBポートをインターネットへ開放しない。

## 8. 秘密情報・ログ

- DBパスワード、Cookie署名/暗号鍵、Spotify client secretは環境変数またはホスティングのSecret Storeで管理する。
- `.env`実ファイル、資格情報、トークンをGitへ追加しない。`.env.example`にはダミー値と説明だけを置く。
- ログにパスワード、Cookie、認証ヘッダー、招待リンク/トークン、OAuthアクセストークン、身体測定値を出さない。
- エラー画面・APIでスタックトレース、SQL、サーバー内部パスを利用者へ返さない。
- ログの保持期間と閲覧権限を限定する。管理者の認証・承認イベントは必要範囲で監査可能にする。

## 9. Spotify将来連携

画面内再生を実装する場合、Spotify OAuthのClient Secretをブラウザーへ含めない。許可スコープを最小化し、refresh tokenを保存するなら暗号化・アクセス制限・失効・アカウント解除を設計する。Spotify Premium要件、端末動作、Spotify Developer Terms/Policyを着手時に確認する。画面内再生条件を満たせない場合は機能を提供しない。

## 10. セキュリティ確認項目

- 未認証、承認待ち、却下アカウントで保護APIへアクセスできない。
- 一般利用者からAdmin APIを実行できない。
- 利用者Aが利用者Bの記録・測定・メニューIDを使って参照、更新、削除できない。
- CSRFトークンなしの状態変更要求が拒否される。
- 招待の再使用、期限切れ、失効後の受諾が拒否される。
- ログ、ブラウザー保存領域、Git差分に秘密情報が残らない。
- 本番DBが公開ネットワークへ直接露出していない。
