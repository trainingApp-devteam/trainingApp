## 2. テスト方針

- 変更に最も近い単体テストを先に実行し、PRではバックエンド・フロントエンドの自動テストを実施する。
- DB制約、認証・認可、複数利用者の分離はMySQLを使う結合テストで確認する。
- 主要ユーザーフローをE2Eで検証し、実装上の単位・状態のずれを検出する。
- UIは狭い画面と広い画面の双方で、入力、エラー、空状態、通信中、権限の表示を確認する。
- テストで実ユーザーの健康データや本番資格情報を使用しない。

## 3. テストレベル

| レベル | 対象 | 主な手段 |
| --- | --- | --- |
| 単体 | 集計、入力検証、招待状態遷移、サービスロジック、画面コンポーネント | JUnit、React Testing Library等 |
| API/DB結合 | Spring Security、REST、MySQL制約、Flyway | Spring Boot Test、MySQLコンテナ等 |
| E2E | 招待から承認、記録、履歴まで | Playwright等 |
| コンテナ | クリーンビルド、Compose起動、healthcheck、volume永続化 | Docker Compose |
| 手動受け入れ | モバイル/PCの操作性、可読性、Spotify将来検証 | 実ブラウザー・端末 |

## 4. 重要なテストケース

### 4.1 認証・Admin承認

| ID | 条件 | 期待結果 |
| --- | --- | --- |
| AUTH-01 | 有効な招待でユーザー名・パスワードを登録 | `PENDING_APPROVAL`で登録され、セッションは発行されない |
| AUTH-02 | 承認待ちユーザーがログイン | ログイン不可。アカウント状態を推測できない共通エラー |
| AUTH-03 | Adminが承認 | 状態が`ACTIVE`となり、本人がログイン可能 |
| AUTH-04 | Adminが却下 | ログイン不可。一般利用者からAdmin APIは実行不可 |
| AUTH-05 | 期限切れ、失効、使用済み招待 | 申請を拒否し、既存ユーザーや招待を変更しない |
| AUTH-06 | 同一正規化ユーザー名を申請 | 一意制約により拒否し、内部情報を返さない |
| AUTH-07 | 本人がアカウント名を変更 | 本人の表示名だけが変わりヘッダーに反映。空白のみ・CSRFなしは拒否。他利用者は変化しない |
| AUTH-08 | パスワード変更 | 現在のパスワード不一致・12文字未満・同一値は拒否。成功後は旧パスワードでログイン不可・新パスワードで可。セッションIDが更新される |

### 4.2 利用者データ分離

利用者A/Bを作成し、Aで作成した記録・測定・メニューのIDをBから参照、更新、削除する。全て拒否され、Aのデータが変化しないこと。統計APIにもBのデータが混入しないこと。

### 4.3 トレーニング記録

- 回数のみ、時間のみ、回数+重量、時間+重量を保存できる。
- 回数と時間の同時指定、両方未入力、0以下の回数/時間、負の重量を拒否する。
- 同日複数の記録を保存し、一覧で区別して表示する。
- メニューから作成した記録が、その後のメニュー変更に影響されない。
- 個別記録削除で関連種目・セットが残らず、他の記録に影響しない。
- 回数/時間の値に対応する係数が登録された場合、セット別推定値・セッション合計がサーバーで計算・保存される。
- 「1種目ずつ実行」で種目を順に実行し、完了した種目だけが1つの記録として保存される。途中で中止しても完了済みの種目は残る。進め方は記録方法の選択画面の「一から種目を作成して記録」の2つの選択肢（ボタン）で選び、記録画面へ`flow=step`で引き継がれる。保存済みメニューも1種目ずつ順に実行できる。
- 記録画面のメニュー作成は1つのフォームで、進め方の表示・区画見出し・ラジオボタンがなく、日付は見出しの横の小さい欄。作成中のセットはモーダルで確認・並べ替え・削除・すべて削除でき、スマートフォン幅でも作成フォームが1画面に収まり横にはみ出さない（E2E）。
- メニュー管理の作成フォームに種目IDの手動追加と追加前の設定欄がなく、部位タブ→種目チップのタップで既定値（有酸素マシンは時間）のまま追加され、回数・時間・負荷を一覧の行で編集して保存できる。空の回数・時間は保存できない。
- 記録詳細で回数を変えたセットは、元のRPEと最新の体重で推定し直される。
- クライアントから偽の係数や消費カロリー値を送っても、保存値に採用されない。
- `POST /calorie-estimates/preview`は保存時と同じ値を返し、`exercise_calorie_estimates`に行を追加しない。メニュー作成画面にセットを追加すると「予定 約X kcal」が表示される（E2E）。
- 種目ごとに記録形式が1つ決まっており（有酸素マシンだけ時間）、メニュー作成・メニュー管理に記録形式を変える部品がない。
- 別ドメイン構成（CORS許可オリジン・`SameSite=None`を設定）で、許可したオリジンだけCORSを許可し、`/auth/csrf`のヘッダーで受け取ったトークンでログインでき、トークンなしは拒否される。CSRFクッキーが`SameSite=None; Secure`になる（`CrossSiteFrontendTest`）。
- 係数未登録の種目/記録形式は未計算となり、記録作成は成功する。
- 係数マスタを改訂しても、過去に記録されたセット別推定値が変化しない。

### 4.4 集計・身体測定

- 最大重量は重量があるセットのみから算出される。
- トレーニング量は回数と重量が両方あるセットだけを`重量×回数`で合算する。
- 時間セット、重量なしセットをトレーニング量に含めない。
- 同一測定項目を同日に複数回保存し、それぞれの測定時刻で表示できる。
- 体重・体脂肪率が項目コード、値、単位と正しく対応する。
- 身長はアカウントに一度だけ登録・修正でき、測定（`height_cm`）としては登録できない。範囲外・小数第2位は拒否する。
- テスト用の追加測定項目をマスタに登録し、DB列追加なしで作成・取得できる。

### 4.4.1 推移・種目

- 種目の作成・変更・削除API（`POST /exercises`、`PUT`/`DELETE /exercises/{id}`）は`405`で、`exercises.owner_user_id`列が存在しない。
- 種目別推移は本人の記録だけを記録ごとに集計し、最大重量・トレーニング量（回数と重量が両方あるセットのみ）・合計回数・合計時間を返す。重量のない記録の最大重量・トレーニング量は`null`。期間指定、`from > to`の`400`、存在しない種目の`404`。
- 記録したことのある種目一覧は本人の記録回数・最終実施日を返し、他利用者の記録を含まない。
- グラフは日付順に描画し、最新値・ツールチップ（ポインター/矢印キー）・数値一覧を表示する。データがない期間は空状態を表示する。
- 体重・体脂肪率の推移は期間を切り替えると開始日時以降の値を再取得する（全期間は開始日時なし）。
- 推移画面・身体測定画面のグラフがダーク背景で可読（E2Eコントラスト検査、スマートフォン幅を含む）。

### 4.4.2 音楽再生

- 「音楽を再生」を押すまでYouTubeのスクリプト・iframeを読み込まない。記録画面ではメニュー作成中に音楽を表示せず、プレイリストを入力して実行開始したときだけ表示・再生する。入力がなければ表示しない。
- 押すと（または実行開始で）入力したプレイリストの埋め込みプレーヤーを表示して再生する。前の曲・一時停止・次の曲・シャッフルが動く。
- プレイリストのURL（youtube.com/youtu.be/music.youtube.comの`list=`）とIDを読み取り、他のサイトや`list=`のないURLは実行を始めずエラーにする。入力したURLは次回の初期値になる。
- 1種目ずつ実行で次の種目を設定する間は一時停止し、次の実行で再開する。
- 埋め込み不可（エラー101/150）などの動画は次の曲へ飛ばして通知し、全曲再生不可ならエラーを表示して止まる。
- タイマー終了音の間だけ音量を下げ、約5秒後に戻す。
- 実ブラウザーで、プレイリストが読み込まれ再生が始まること（手動・E2E環境で確認）。

### 4.5 CSV・削除範囲

- CSVエクスポートAPI・画面が初期リリースに存在しない。
- 個別記録の削除は可能。
- アカウント削除・全件削除用APIや画面も存在しないことを確認する。

### 4.6 Docker・DB

- クリーン環境でイメージをビルドしComposeを起動できる。
- DB healthcheck前にAPIが誤って正常扱いにならない。
- 通常停止・再起動後もMySQLのデータが残る。
- Flywayを空DBへ適用でき、seedを複数回適用しても重複しない。
- 明示的なvolume削除以外でDBデータが消えない。

### 4.7 カロリー推定

- すべての種目に有効な係数がある（V10）。筋トレ種目は回数・時間の両方、有酸素マシンは時間のみ推定でき、`GET /exercises`の`calorieBases`と一致する。
- RPE帯境界（REP 6/7、MINUTE 4/5/7/8）で適用METが一意に決まる。
- 体重70kg、8回、RPE 6は3秒/回・3.5 METの仮定で約1.72 kcalとなる。
- 同条件でRPE 8は6.0 METとなり、推定値と係数IDがDBへ保存される。
- 時間形式は入力秒数で計算し、休憩時間を含めない。
- 体重範囲外、未対応種目、誤ったbasisでは推定を拒否し、推定行を作らない。
- 推定履歴はMySQL再起動後も保持される。
- 身体測定で登録した最新の体重がセット追加時に自動で使われ、セット画面で体重を再入力しない。
- 体重未登録時は身体測定への案内を表示し、カロリー推定対象セットを登録できない。
- 有酸素マシンを選ぶと記録形式が時間に固定される。推定に失敗したセットがあっても記録は保存され、未計算として表示される。
- RPEの「？」ヘルプはマウスホバーとキーボードフォーカスで表示できる。

## 5. MVP受け入れ条件

- 一般利用者2名と開発者Admin1名の想定で、招待・承認を含む主要経路を完了できる。
- 承認前ログイン不可、承認後ログイン可。
- 一般利用者間の記録・測定・メニュー分離をサーバー側で保証する。
- 回数/時間と任意重量の記録、同日複数トレーニング、履歴・推移表示が利用できる。
- 体重・体脂肪率の同日複数測定、身長の一度だけの登録、将来項目追加可能なデータモデルを確認できる。
- 消費カロリー係数をDBへseedし、該当するセットの推定値を計算・永続化できる。
- CSVエクスポートがMVPの画面/APIに含まれない。
- PCおよびスマートフォンで主要画面が操作できる。
- Docker Composeで起動し、MySQLデータが再起動後も保持される。

## 6. PR/リリース確認ゲート

1. 変更範囲の単体テストと静的検査が成功する。
2. API/DB変更がある場合、MySQL結合テストとFlyway適用を確認する。
3. 認証・所有者・Admin権限に関わる変更は、許可/拒否両方のテストを必須とする。
4. 画面変更は主要な狭幅・広幅レイアウトで確認する。
5. リリース前にE2E主要経路、バックアップ/復元、公開設定チェックを行う。
