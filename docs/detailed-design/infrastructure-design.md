## 2. ローカル開発構成

Docker Composeで次のサービスを起動する。

| Service | 役割 | 開発時の公開範囲 |
| --- | --- | --- |
| `frontend` | React + TypeScriptの開発サーバー | 開発PCのブラウザーからアクセス |
| `backend` | Java Spring Boot API | frontendからComposeネットワーク経由でアクセス |
| `db` | MySQL | Compose内部。開発確認用に`127.0.0.1:3306`だけへ公開 |

サービス間通信は専用Composeネットワークを使う。backendのDB接続先はComposeのサービス名`db`とし、コンテナ内から`localhost`でDBへ接続しない。

### 2.1 永続化とヘルスチェック

- MySQLデータ領域にnamed volumeを設定する。
- 通常の停止・再起動でDBデータが残ることを確認する。
- DB healthcheck成功後にbackendを開始する。アプリ起動時も接続再試行または明示的な起動失敗を実装する。
- `docker compose down`と、データを消す`down -v`相当の操作をREADMEで明確に区別する。
- DBポートを公開する場合はlocalhostに限定し、公開環境ではDBポートをインターネットへ公開しない。

### 2.2 設定値

`.env.example`にキー名・用途・ダミー値だけを記載する。実際の`.env`はGit管理対象外とする。

想定する設定例:

- `MYSQL_DATABASE`, `MYSQL_USER`, `MYSQL_PASSWORD`, `MYSQL_ROOT_PASSWORD`
- `SPRING_DATASOURCE_URL`, `SPRING_DATASOURCE_USERNAME`, `SPRING_DATASOURCE_PASSWORD`
- `APP_SESSION_COOKIE_SECURE`
- `APP_ADMIN_BOOTSTRAP_USERNAME`と初期化時にのみ使う初期資格情報

初期資格情報を通常起動のたびに上書きしない。必須設定が不足した場合は、安全でない既定値で起動せずエラー終了する。

### 2.3 開発者起動手順

Docker Desktopを起動し、リポジトリルートで`docker compose up --build`を実行する。画面は`http://localhost:5173`、推定APIは`http://localhost:8080`、MySQLは`127.0.0.1:3306`で利用する。Spring Boot起動時にFlywayが標準種目とRPE帯別係数をseedする。通常停止は`docker compose down`、DBを初期化してseedをやり直す場合だけ`docker compose down -v`を使う。

### 2.4 テスト環境（本番公開を含まない）

テスト用サーバーを別途契約せず、既存の開発PCをDocker Composeホストとして利用する。追加のクラウド利用料、独自ドメイン、マネージドDBは不要で、インフラ費用は0円を目標とする。

| Service | 役割 | 接続方針 |
| --- | --- | --- |
| `frontend` | Reactのテスト用画面配信 | ホストへ公開する入口。`/api`をbackendへ転送 |
| `backend` | Spring Boot API | Compose内部のみ。frontendから接続 |
| `db` | MySQL | Compose内部のみ。named volumeでテストデータを保持 |

PCのブラウザーは`http://localhost:5173`でアクセスする。frontendとbackendはVite proxy/Composeネットワーク経由で接続する。MySQLのホスト公開は`127.0.0.1`に限定し、LANやインターネットへ公開しない。スマートフォンからの確認では開発用にfrontendポートだけLANへ一時公開し、DBポートは公開しない。

同じLAN外のテスターに一時共有する必要がある場合のみ、開発PCでCloudflare Quick Tunnelを起動し、frontendのホスト側ポートへ接続する。Quick Tunnelはアカウントと独自ドメインなしで一時URLを発行できるが、プロセス停止でURLが無効になり、再起動時は別URLとなる。URLを知る人はアクセスできるため、メール制限を有効にし、テスト専用の架空データだけを使う。PCとトンネルが稼働中でなければ利用できず、稼働保証もない。

このテスト構成ではOS上のDocker環境、PCの電気代・ネットワーク費用は既存環境を利用する前提で、追加料金には算入しない。ComposeのDB資格情報はローカル検証専用であり、公開環境へ流用しない。テストデータは永続保管対象ではなく、DB初期化や`docker compose down -v`で削除される。

## 3. コンテナ・バージョン方針

- Node.js、JDK、MySQLのサポート中バージョンを実装開始時に選定し、Dockerfile/Composeで固定する。
- 再現性のため`latest`タグに依存しない。
- 本番用イメージでは開発依存・不要なビルドツールを含めない。
- DBスキーマはFlyway等で管理し、アプリ起動時の適用方針を一元化する。
- ソースをbind mountする開発設定と、本番のimmutable image設定を混在させない。

## 4. 参考：将来の公開構成候補（今回の対象外）

以下は今回決めない将来公開時の参考情報であり、テスト環境のために契約・構築しない。

| 構成 | 適する条件 | 確認点 |
| --- | --- | --- |
| さくらのVPS 2GB + Docker Compose | 少人数向けに低額で継続公開したい。推奨案 | 年額19,118円（月換算約1,594円）+ `.com`年額3,220円（月換算約268円）。合計約1,862円/月相当。メモリ負荷試験と監視が必要 |
| Oracle Cloud Always Free A1 + Docker Compose | サーバー費用0円を優先し、停止・回収リスクを許容できる | 合計2 OCPU/12GB相当等が無料枠だが、独自ドメイン・一部バックアップ費用は別。ホームリージョンの容量不足、7日間の低利用による回収、仕様変更がある。外部バックアップ必須 |
| 静的ホスティング + Java APIホスト + マネージドDB | 各サービスを分離したい、DB運用を委任したい | 無料枠・月額、Java実行時間、スリープ、RAM、転送量、永続性、DB接続、バックアップを個別確認 |
| マネージドMySQL + APIホスト | DB運用負荷を下げたい | 無料枠の有無、容量、接続数、バックアップ復元、料金超過条件 |

推奨する2GB VPS構成では、Caddy、React静的ファイル、Spring Boot、MySQLを同じホストで運用する。3アカウント程度の低頻度利用を前提とし、公開前に負荷試験を行う。OOMや継続的なメモリ逼迫があれば4GBへ増強する。Cloudflare Pagesで静的配信を分離してもVPS料金は下がらず、Cookie/CSRF/CORS設定が複雑になるため初期案では採用しない。

Oracle Cloud Always Freeを利用する場合は、無料枠の詳細と回収条件を公式文書で確認する。MySQL互換DB候補としてTiDB Cloud Starter等も調査対象にできるが、MySQLと全機能・運用挙動が同じとはみなさず、SQL互換性とマイグレーションを検証する。無料枠の金額・条件は変更されうるため、契約前に公式価格表・規約を確認し、確認日を記録する。

## 5. 公開環境の構成要件

- HTTPSを必須とする。
- 可能ならフロントエンドとAPIを同一オリジンで配信し、Cookie/CORS設定を単純化する。
- DBはプライベートネットワークまたはサービス内部接続に限定する。
- Secret StoreへDB資格情報等を設定し、ビルド成果物やGitへ含めない。
- Oracle Cloud Always Freeを使う場合、容量不足とアイドルインスタンス回収による停止を前提に運用・復旧手順を用意する。無料枠でも無停止やSLAは保証されない。
- GitHub Actions、GHCR、Cloudflare R2等の無料枠を使う場合、枠の上限と超過料金を監視し、必要に応じて支出上限を設定する。
- 無料枠を超えた場合の料金発生・停止条件を確認し、予算上限や利用停止手段を決める。
- Spotifyを追加する段階ではOAuth callback URL、HTTPS、secret保管、Spotify側の開発モード制約も確認する。

## 6. バックアップ・復旧

- CSVエクスポートは初期リリースに含めない。DBのバックアップ/復旧は独立した運用手順として用意し、初期版で利用者が自分のデータをCSV取得できるとは想定しない。
- マネージドDBを使う場合、バックアップ自動化の有無、保持期間、復元時点、復元料金を契約前に確認する。
- 自前バックアップを行う場合、暗号化し、本番DBと異なる保存先に保管する。アクセス権は最小限にする。
- Cloudflare R2はStandardストレージ月10GB-month、Class A操作100万回、Class B操作1,000万回まで無料。上限超過時は従量課金となるため、日次バックアップ30日分が容量内に収まるか確認する。
- 初期運用頻度は日次、保持期間は直近30日を候補とし、記録頻度・損失許容時間・保存料金を見て公開前に確定する。
- バックアップを別環境へ復元するテストを定期的に行い、手順と結果を記録する。
- アカウント・全データ削除機能はないため、利用停止/アカウント停止の運用とデータ保持方針を公開前に決める。

## 7. 運用確認

- 起動状態とヘルスチェック、アプリのエラー率を確認できる手段を用意する。
- ログにはrequest ID、日時、処理結果等を記録し、パスワード、Cookie、招待token、身体測定値を記録しない。
- Java/Node/MySQLのセキュリティ更新を確認し、更新時は自動テストとマイグレーションを実行する。
- DB容量、無料枠、請求通知、バックアップ成功を定期確認する。
- 障害対応時にDBを直接手修正せず、バックアップ取得・原因調査・復旧の順で進める。

## 8. 公開前チェックリスト

- 無料枠・有料時料金、上限、停止条件を公式情報で確認済み。
- DBの永続化、バックアップ、復元手順をテスト済み。
- HTTPS、Cookie属性、CORS、DB非公開、Secret設定を確認済み。
- 利用者とAdminの権限、承認待ちの扱いを本番設定で確認済み。
- データ保持・プライバシー告知・障害連絡方法を合意済み。
