# 詳細設計書一覧

## 文書の位置付け

概要と共通方針は[概要設計書](../overview-design.md)を参照する。本フォルダー内の文書は、その方針を実装・レビュー・テストできる粒度にした詳細設計である。

## 文書一覧

| 文書 | 主な担当者・関心領域 | 内容 |
| [アーキテクチャ設計書](../architecture.md) | 全開発者、インフラ担当 | 配置図、サービス構成、通信経路、公開案と代替案 |
| --- | --- | --- |
| [業務機能設計書](functional-design.md) | プロダクト担当、フロント/バックエンド開発者 | 利用フロー、状態遷移、業務ルール、機能受け入れ条件 |
| [データ設計書](data-design.md) | DB/バックエンド開発者 | ER図、テーブル定義、制約、インデックス、変更方針 |
| [API設計書](api-design.md) | フロント/バックエンド開発者 | HTTP API、認証要件、リクエスト/レスポンス、エラー |
| [画面設計書](screen-design.md) | フロントエンド開発者、UIレビュー担当 | 画面構成、レイアウト、入力、状態表示、レスポンシブ方針 |

## 変更ルール

- 各設計事項の詳細は所有する文書を正本とする。他文書では必要な要約とリンクに留める。
- APIの振る舞いを変える場合はAPI設計書と業務機能設計書、必要に応じて画面・テスト設計書も更新する。設計書の更新は、`main` へのプルリクエストを作るときにブランチの変更をまとめて行う（`docs/openapi.yaml` は実装と同じコミットで更新する）。
- DB項目を変える場合はデータ設計書を更新し、API・画面・移行テストへの影響を確認する。
- 合意前の案には「案」または「未決」と明示し、確定仕様と混同させない。
- 外部サービスの無料枠・規約・料金は変わりうるため、採用直前に公式情報と確認日を記録する。
