本書は画面の情報配置と操作を定義する。色、書体、アイコン等の最終デザインシステムはフロントエンド実装時に決める。画面の文言だけでなく、通信中・空・エラー・権限なしの状態も実装対象とする。

## 2. ナビゲーション

### 2.1 一般利用者

主要画面は「ホーム」「記録」「履歴」「身体測定」「メニュー」「アカウント」。全画面共通のヘッダーに、ロゴ（ホームへ）、日付、ログイン状態、ハンバーガーメニューを置く。画面ごとに同じリンクを重複して並べず（ホームのクイックリンク等は設けない）、画面遷移はハンバーガーメニュー（記録・履歴・メニュー・身体測定・アカウント）に集約する。メニューは現在ページを強調し、Escape・外側クリック・ページ移動で閉じる。

### 2.2 Admin

一般利用者の画面に加え、「招待」「承認待ち」を表示する。Adminであっても一般画面で他ユーザーの記録を閲覧する導線は設けない。

## 3. レスポンシブ方針

- 狭い画面では1カラムを基本とし、セット入力と主要アクションを優先表示する。
- 広い画面では履歴一覧と詳細、またはフォームと補助情報を並べられる。
- 画面幅で情報の意味や権限を変えない。横スクロールが必要な大きな表を避ける。
- 入力欄の高さ、タップ対象、フォーカス表示を確保する。PCでもキーボード操作を可能にする。
- グラフには数値、単位、期間を併記し、色だけで情報を伝えない。

具体的なブレークポイントはCSS実装時に一元管理する。初期案はモバイル、タブレット、デスクトップの3段階とし、端末実測で調整する。

## 4. 画面仕様

### 4.1 ログイン

**目的**: 有効な利用者の認証。

**要素**: ユーザー名、パスワード、ログインボタン（画面内に1つだけ。ヘッダーのログインリンクはこの画面では表示しない）、入力エラー、認証失敗メッセージ、「新規登録」への切替リンク。Enterキーでも送信できる。

**状態**:
- 初期: 入力可能。
- 通信中: 二重送信防止、処理中表示。
- 成功: ログイン前に開こうとしていた画面へ遷移する（なければホーム）。
- 失敗: アカウントの存在や状態を推測できない共通メッセージを表示。

承認待ちアカウントはログインできない。パスワードリセット導線は運用方式が決まるまで表示しない。

**新規登録**: 同じ画面で「新規登録」へ切り替える（招待コード、表示名、ユーザー名、パスワード。送信ボタンは「登録申請」）。申請後はAdminの承認を待ち、「ログインへ戻る」で切り替える。

**ログイン必須**: ホームとアカウント以外の全画面（記録・履歴・履歴詳細・メニュー・身体測定）は、未ログインでは表示せずログイン画面へ移動する。ホームは未ログインでは「ログインしてください」の案内だけを表示し、「今すぐ記録」「メニューを作成」などの操作は出さない。

### 4.2 ホーム

**目的**: 今日の記録を始め、直近の状態を把握する。

**レイアウト**:
- 上部: 日付と利用者メニュー。
- 主領域: 「トレーニングを記録」操作、メニューから開始する操作。
- 下部/補助領域: 直近の記録、最近の身体測定への導線。

初回利用時は空状態と記録開始操作を表示する。統計情報がない場合に空のグラフを誤認させない。

### 4.3 トレーニング入力

**目的**: セットを素早く記録する。

**入力順**:
1. 実施日（初期値は今日）と任意メモ。
2. 種目を検索・選択。

注: 開発方針変更により、モーダル式の種目検索は採用しません。画面では「部位（グループ）を選択 → そのグループ内の種目をセレクトする」方式を採用し、シンプルなドロップダウンで種目選択を行います（実装参照: frontend/src/pages/Record.tsx）。
3. 各種目にセットを追加。
4. セットごとに「回数」または「時間」を選択し、数値と任意重量kgを入力。
5. RPE 1〜10を入力する。RPE横の「？」をホバーまたはフォーカスすると、余力回数による目安を表示する。推定用体重はアカウント登録値を使用し、この画面では入力しない。未登録ならアカウント画面への案内を表示する。
6. 保存し、記録詳細またはホームへ戻る。

**レイアウト**:
- モバイル: 種目ごとの縦並び領域。セット入力は「セット番号 / 回数・時間 / 重量 / RPE / 推定kcal / 行操作」の順。
- PC: 同じ情報をテーブル状に整列可能。ただし狭い幅へ戻ったときに横溢れしない。
- 追加操作: セット追加、種目追加、選択済み種目の順序変更。

**入力検証**:
- 回数と時間を同じセットに同時入力できない。
- 選択された形式の値は正数。重量は任意で0以上。
- エラーを対象入力の近くに表示し、保存失敗時に入力値を保持する。
- 保存中は二重送信を防止する。
- 消費カロリーのMET係数はサーバーが管理し、保存時に計算する。クライアントからMET/kcal値を送らない。
- RPEはセット終了時にフォームを保ってあと何回できるかを目安に選ぶ。未登録の体重が必要な場合、推定対象セットを追加できない。
- 独自種目と「ダンベル」「スミスマシン」「パワーラック」のような器具項目は計算対象外と表示する。
- 推定に使った体重、RPE、回数/時間、係数版、結果をDBへ保存する。休憩時間は含めない。

### 4.4 種目選択

標準種目と本人の独自種目を検索する。結果には名称とカテゴリを表示する。既に記録へ追加された種目を選択した場合の扱いは重複許可とし、利用者が意図的に複数項目を持てる案を採用する。独自種目の編集・削除は本人所有の項目のみ可能。

### 4.5 履歴一覧・詳細

**一覧**: 日付降順。期間・種目フィルター、ページング、空状態を提供する。同日の記録は時刻順で区別する。

**詳細**: 実施日、メモ、種目ごとのセット表、計算可能なセットの消費カロリー推定値とセッション合計を表示する。推定値であることを明記し、未計算セットをゼロkcalと誤認させない。編集・個別削除は確認操作を挟み、削除後に関連セットも消えることを確認する。他ユーザーの記録へのリンクやID入力機能は設けない。

### 4.6 メニュー管理

メニュー一覧、作成、編集、個別削除を提供する。メニューは名前、説明、種目と順序を管理する。初期仕様では目標回数・時間・重量を保存しない。「このメニューで記録」操作で種目構成を新規記録へ複製し、その後の記録編集はメニューへ反映しない。

### 4.7 推移

種目別推移は期間を選び、最大重量と重量×回数によるトレーニング量を表示する。記録詳細では消費カロリー推定値も表示する。時間形式や重量未入力のセットは該当する重量集計から除外し、除外条件を凡例または補助情報で明らかにする。

グラフが描画できない場合やデータがない場合も、対象期間・数値一覧・空状態を表示する。

### 4.8 身体測定

初期項目は身長(cm)、体重(kg)。測定項目、数値、測定日時を入力する。同じ日に複数の測定を登録できる。履歴は項目と日時で絞れる。将来項目の追加は項目マスタを画面に反映し、単位付きで入力・表示する。

### 4.9 Admin: 招待・承認

- 招待発行後、秘密の招待リンクを一度だけ表示する。再表示はせず、必要なら旧招待を失効させて再発行する。
- 承認待ち一覧には申請ユーザー名、表示名、申請日時を表示する。
- 承認・却下は確認操作を行う。承認前後の状態が一覧上で分かる。
- Admin画面から一般利用者の筋トレ・測定データを閲覧できない。


### 4.10 アカウント

表示名、推定用体重の登録・更新を提供する（ログアウトはヘッダーの操作に一本化）。体重は20〜300kgで入力し、サーバーのアカウント情報（`users.body_weight_kg`）に保存し、ブラウザーには推定用のキャッシュとして保持する。本人データCSVエクスポート、アカウント削除、全データ一括削除のボタンは初期リリースでは表示しない。

## 5. 共通UI状態とアクセシビリティ

- 各通信画面にローディング、成功、失敗、空状態を定義する。
- フォームにはラベル、説明、項目単位エラーを付ける。プレースホルダーだけで項目名を表現しない。
- フォーカス順を論理的にし、主要操作はキーボードで実行できる。
- 状態やチャートは色だけに依存せず、テキスト・数値・アイコン等を併用する。
- 削除など取り消しにくい操作は確認し、対象名を明示する。
- レスポンシブ表示で長いユーザー名、種目名、エラー文が重ならないことを確認する。
