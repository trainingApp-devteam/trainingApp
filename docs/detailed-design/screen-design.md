## 2. ナビゲーション

### 2.1 一般利用者

主要画面は「ホーム」「記録」「履歴」「推移」「身体測定」「メニュー」「アカウント」。全画面共通のヘッダーに、ロゴ（マスコットのカワウソのアイコン＋「TrainingApp」。ホームへ）、ログイン状態、ハンバーガーメニューを置く（日付は表示しない）。画面ごとに同じリンクを重複して並べず（ホームのクイックリンク等は設けない）、画面遷移はハンバーガーメニュー（記録・履歴・メニュー・推移・身体測定・アカウント）に集約する。メニューは現在ページを強調し、Escape・外側クリック・ページ移動で閉じる。

### 2.2 Admin

一般利用者の画面に加え、「招待」「承認待ち」を表示する。Adminであっても一般画面で他ユーザーの記録を閲覧する導線は設けない。

### 2.3 マスコット・アイコン

マスコットはダンベルを持ったカワウソ（`frontend/public/otter.svg`、背景はアプリの基調色の藍色の角丸四角）。ファビコン、ホーム画面に追加したときのアイコン（`apple-touch-icon.png`、`icon-192.png`、`icon-512.png`、`manifest.webmanifest`）、ヘッダーのロゴに使う。PNGはSVGから生成する。

## 3. レスポンシブ方針

- 狭い画面では1カラムを基本とし、セット入力と主要アクションを優先表示する。
- 広い画面では履歴一覧と詳細、またはフォームと補助情報を並べられる。
- 画面幅で情報の意味や権限を変えない。横スクロールが必要な大きな表を避ける。
- 入力欄の高さ、タップ対象、フォーカス表示を確保する。PCでもキーボード操作を可能にする。
- グラフには数値、単位、期間を併記し、色だけで情報を伝えない。

具体的なブレークポイントはCSS実装時に一元管理する。初期案はモバイル、タブレット、デスクトップの3段階とし、端末実測で調整する。

## 4. 画面仕様

### 4.1 ログイン

**目的**: 有効な利用者の認証。

**要素**: ユーザー名、パスワード、ログインボタン（画面内に1つだけ。ヘッダーのログインリンクはこの画面では表示しない）、入力エラー、認証失敗メッセージ、「新規登録」への切替リンク。Enterキーでも送信できる。

**状態**:
- 初期: 入力可能。
- 通信中: 二重送信防止、処理中表示。
- 成功: ログイン前に開こうとしていた画面へ遷移する（なければホーム）。
- 失敗: アカウントの存在や状態を推測できない共通メッセージを表示。

承認待ちアカウントはログインできない。パスワードリセット導線は運用方式が決まるまで表示しない。

**新規登録**: 同じ画面で「新規登録」へ切り替える（招待コード、表示名、ユーザー名、パスワード。送信ボタンは「登録申請」）。申請後はAdminの承認を待ち、「ログインへ戻る」で切り替える。

**ログイン必須**: ホームとアカウント以外の全画面（記録・履歴・履歴詳細・メニュー・身体測定）は、未ログインでは表示せずログイン画面へ移動する。ホームは未ログインでは「ログインしてください」の案内だけを表示し、「今すぐ記録」「メニューを作成」などの操作は出さない。

### 4.2 ホーム

**目的**: 今日の記録を始め、直近の状態を把握する。

**レイアウト**:
- 主領域: 「トレーニングを記録」操作、メニューから開始する操作。
- 下部/補助領域: 直近の記録、最近の身体測定への導線。

初回利用時は空状態と記録開始操作を表示する。統計情報がない場合に空のグラフを誤認させない。

### 4.3 トレーニング入力

**目的**: セットを素早く記録する。

**入力順**:
1. 実施日（初期値は今日）と任意メモ。
2. 種目を検索・選択。

注: 開発方針変更により、モーダル式の種目検索は採用しません。画面では「部位（グループ）を選択 → そのグループ内の種目をセレクトする」方式を採用し、シンプルなドロップダウンで種目選択を行います（実装参照: frontend/src/pages/Record.tsx）。
3. 各種目にセットを追加。
4. セットごとに「回数」または「時間」を選択し、数値と任意重量kgを入力。
5. 予定RPE 1〜10を入力する（消費カロリーの見積もり用。実際のRPEは実行中に各セットで入力する）。RPE横の「？」をホバーまたはフォーカスすると、余力回数による目安を表示する。推定用体重は身体測定の最新の体重を使用し、この画面では表示も入力もしない。未登録のまま推定対象のセットを追加しようとしたときだけ、身体測定で体重を登録するよう案内するエラーを表示する。
6. 保存し、記録詳細またはホームへ戻る。

**記録方法の選択（`/record/select`）**: 見出しと、縦に並べた3つのボタンだけを置く（説明文・区画見出し・ラジオボタンは置かない）。「まとめて実行」（主ボタン、`/record?mode=create`）、「1種目ずつ実行」（主ボタン、`/record?mode=create&flow=step`）、「保存済みメニューから」（副ボタン、`/record/select-menu`）。配色は`styles/ui.ts`の`btnPrimary`/`btnSecondary`。保存済メニューからの記録は「まとめて実行」で行う（記録画面は`flow=step`付きの保存済メニュー開始にも対応しているが、この画面からは使わない）。

**画面の構成（メニュー作成）**: 縦に長くならないよう、見出しの横に日付、その下に1枚のフォーム（`form`「メニュー作成」）だけを置き、区画ごとの見出しは付けない。スマートフォン幅（375px）でもフォーム全体が1画面に収まり、横にはみ出さないこと。保存済みメニューを選んで適用する操作は、この画面には置かない（保存メニューからの開始は「保存済メニューを選択」画面から行う）。進め方はこの画面では選ばず表示もしない。URLの`flow`で受け取る（ヘッダーの「記録」から直接開いた場合は「まとめて実行」）。
- 見出し行: 「メニュー作成」と、右側に小さい日付欄（実施日）。
- 完了した種目（1種目ずつ実行で、完了した種目があるときだけ）: 「完了: 1. 種目名（Nセット） / 2. …」の1行。
- 種目: 部位と種目のセレクトを横に並べる。
- 値: 回数または秒数の入力と単位（「回」/「秒」）、負荷kg（任意）を1行に並べる。記録形式は種目ごとに決まっており（API の`recordType`。有酸素マシンは時間、それ以外は回数）、変更する部品は置かない。
- 予定RPE: スライダー、値、「？」（目安の説明。行の幅に収める）と、同じ行の右端に「セットを追加」。
- 実行時に流すプレイリスト（YouTubeのURL・任意）。
- 入力エラーと完了通知。
- 予定の消費カロリー: 作成中のセットの見積もり合計「予定 約12.3 kcal」（計算中は「（計算中）」を付ける）。セットを追加すると、`POST /calorie-estimates/preview`で予定RPEを使って1セットずつ見積もる。
- 操作: 「作成中のセット（N）」（モーダルを開く）、まとめて実行では「実行開始」、1種目ずつ実行では「この種目を実行」。完了した種目があれば「完了して記録」。その下に作成中のセットの要約（「種目名×セット数」）を1行で表示する。

**作成中のセット（モーダル）**: 「作成中のセット（N）」で開き、✕・背景・Escキーで閉じる。セットを1行ずつ（番号、種目名、「回数/秒数 · 負荷 · 予定RPE · 予定 約X kcal」、↑↓×）表示し、セットがあれば「すべて削除」を置く。保存済みメニューを1種目ずつ実行するときは、未実行の種目を「このあとの種目: A → B」と表示する。

**音楽（実行中だけ表示）**: メニュー作成では表示しない。「実行開始」（または「この種目を実行」）を押したとき、プレイリスト欄に入力があればYouTubeプレイリストの埋め込みプレーヤー（16:9、200×200px以上）を実行画面の下に表示して再生を始める。入力がなければ音楽は流さない。URL（`list=`を含むyoutube.com/youtu.be/music.youtube.comのURL）またはプレイリストIDを受け付け、読み取れなければ実行を始めずエラーを表示する。入力したURLは端末のブラウザーに保存し、次回の初期値にする。「前の曲」「再生/一時停止」「次の曲」「シャッフル」、再生できない動画の通知、全曲再生不可のエラー、画面ロック・別アプリ切替で止まることと広告の注記、「音楽を閉じる」は従来どおり。1種目ずつ実行で次の種目を設定する間はプレーヤーを隠して一時停止し、次の実行で再開する。

**実行画面**: 現在のセットの下に「このセットのきつさ（RPE）」のスライダー（初期値は予定RPE、「終わったら、あと何回できそうだったかで選ぶ」を添える）を置き、記録時はこの値で消費カロリーを計算し直す。全メニュー一覧の推定kcal列は予定の見積もりを表示する。最後のセットのボタンは、まとめて実行では「完了して記録」（保存して履歴へ）、1種目ずつ実行では「この種目を完了」（完了した種目へ移して設定画面へ戻り、「『種目名』が完了しました」を表示）。1種目ずつ実行では見出しに「N種目目・現在のセット」を表示する。「中止」は設定画面へ戻り、完了済みの種目は保持する。保存失敗時のエラーは実行画面にも表示する。

**レイアウト**:
- モバイル・PC共通: 作成中のセットはモーダル内で1セット1行（「セット番号 / 種目 / 回数・時間 · 重量 · RPE · 推定kcal / 行操作」）。狭い幅でも横溢れしない。
- 追加操作: セット追加、種目追加、選択済み種目の順序変更。

**入力検証**:
- 回数と時間を同じセットに同時入力できない。
- 選択された形式の値は正数。重量は任意で0以上。
- エラーを対象入力の近くに表示し、保存失敗時に入力値を保持する。
- 保存中は二重送信を防止する。
- 消費カロリーのMET係数はサーバーが管理し、保存時に計算する。クライアントからMET/kcal値を送らない。
- RPEはセット終了時にフォームを保ってあと何回できるかを目安に選ぶ。未登録の体重が必要な場合、推定対象セットを追加できない。
- 全標準種目を推定対象とする。記録形式は種目ごとに固定（V12の`exercises.record_type`）で、メニュー作成・メニュー管理では変更できない。推定できないセット（固定前に保存したメニューで有酸素マシンに回数を設定していた場合）は「kcal対象外」と表示し、保存は止めない。
- 推定に使った体重、RPE、回数/時間、係数版、結果をDBへ保存する。休憩時間は含めない。

### 4.4 種目選択

標準種目だけを部位→種目の順に選ぶ。利用者が種目を作成・編集・削除する画面（旧「独自種目作成」モーダル）は廃止した。既に記録へ追加された種目を選択した場合の扱いは重複許可とする。

### 4.5 履歴一覧・詳細

**一覧**: 日付降順。期間・種目フィルター、ページング、空状態を提供する。同日の記録は時刻順で区別する。

**詳細**: 実施日、メモ、種目ごとのセット表、計算可能なセットの消費カロリー推定値とセッション合計を表示する。編集で回数・時間を変えたセットは、保存時に元のRPE（不明な場合は6）と最新の体重で推定し直す。推定値であることを明記し、未計算セットをゼロkcalと誤認させない。編集・個別削除は確認操作を挟み、削除後に関連セットも消えることを確認する。他ユーザーの記録へのリンクやID入力機能は設けない。

### 4.6 メニュー管理

メニュー一覧、作成、編集、個別削除を提供する。

**作成・編集フォーム**: 「新規作成」または「編集」で一覧の上に開く（開いている間は「新規作成」を隠す）。部品は次の3つに絞る。
1. 名前。
2. 種目を追加: 部位のタブ（ボタン、選択中は`aria-pressed`）と、その部位の種目のチップ。チップをタップすると既定値（回数8回。有酸素マシンは時間60秒）で末尾に追加する。種目IDを直接入力する追加（旧「手動追加」）と、追加前の回数/時間・負荷の設定欄（旧「候補を追加」）は廃止した。
3. メニューの種目: 行ごとに種目名、回数または秒数と単位（種目ごとに固定。変更不可）、負荷kg（任意）、↑↓、×（削除）。値はこの行で直接編集する。保存時に回数・時間が1以上の整数、負荷が0以上であることを検証し、エラーは「『種目名』の回数は…」の形で表示する。

メニューは名前、説明、種目と順序を管理する。初期仕様では目標回数・時間・重量を保存しない。「このメニューで記録」操作で種目構成を新規記録へ複製し、その後の記録編集はメニューへ反映しない。

### 4.7 推移

**種目別の推移（`/progress`、メニュー名「推移」）**: 上部に「種目」セレクト（記録したことのある種目。「種目名（記録回数）」、最終実施日の新しい順）と期間切替（1か月/3か月/1年/全期間、初期値3か月）。下部に記録ごとの折れ線グラフを指標ごとに縦に並べる: 最大重量(kg)、トレーニング量(kg)、合計回数(回、重量のない種目のみ)、合計時間(分)、推定消費カロリー(kcal)。値のない指標のグラフは出さない。時間形式や重量未入力のセットは重量集計から除外し、除外条件をグラフ見出しの下に明記する。記録がない場合は「トレーニングを記録」への導線を表示する。

**グラフ共通仕様（`components/LineChart.tsx`）**:
- 1グラフ1系列の折れ線（2px）と点（直径8px、背景色の縁取り）。単位の違う指標を1つのグラフに重ねない（二軸にしない）。色はダーク背景で検証済みの系列色`#3987e5`。
- 見出しに指標名・単位と「最新 値 単位（日付）」、線の右端に最新値を直接表示。グリッドは1pxの控えめな横線、縦軸は1・2・5刻みの目盛り。
- ポインターを乗せる/タップすると最寄りの点に縦線を合わせ、値と日付のツールチップを表示。グラフにフォーカスして左右矢印・Home/Endで値を読み上げ可能。
- 「数値一覧を表示」で全値の表（新しい順）を開ける。色に頼らず値を確認できる。
- 描画幅は表示幅に合わせ、スマートフォン幅でも文字を実寸で表示する。
- データがない期間は空のグラフを描かず「この期間のデータがありません」と表示する。

### 4.8 身体測定

画面は上から「身長」「体重・体脂肪率を登録」「推移」「履歴」の4区画とする。

- **身長**: 基本的に変わらないため一度だけ登録する。未登録なら身長(cm)の入力と「登録」、登録済みなら値と「修正」ボタン（入力誤りの訂正用。「保存」「キャンセル」）を表示する。50〜300cm、小数第1位まで。測定履歴には含めない。
- **体重・体脂肪率を登録**: 測定日時、体重(kg)、体脂肪率(%)を入力する（身長欄は置かない）。同じ日に複数の測定を登録できる。
- **推移**: 期間切替（1か月/3か月/1年/全期間、初期値3か月）と、体重(kg)・体脂肪率(%)の折れ線グラフ（グラフ共通仕様は4.7）。登録・削除すると再描画する。
- **履歴**: 同じ測定日時の値を1行にまとめ「体重 ○kg / 体脂肪率 ○%」で表示し、行ごとに削除できる。

ホームの「現在の身体データ」は、身長にアカウントの登録値（測定日時は表示しない）、体重・体脂肪率に最新の測定値と測定日時を表示する。

### 4.9 Admin: 招待・承認

- 招待発行後、秘密の招待リンクを一度だけ表示する。再表示はせず、必要なら旧招待を失効させて再発行する。
- 承認待ち一覧には申請ユーザー名、表示名、申請日時を表示する。
- 承認・却下は確認操作を行う。承認前後の状態が一覧上で分かる。
- Admin画面から一般利用者の筋トレ・測定データを閲覧できない。


### 4.10 アカウント

ログイン中は「ログイン中: 表示名（ロール）」とユーザー名（ログインID）を表示し、次の2つのフォームを置く（ログアウトはヘッダーの操作に一本化）。推定用体重の説明文（「カロリー推定に使う体重は…」）は表示しない。

- **アカウント名の変更**: アカウント名（表示名）を1〜100文字で入力し「アカウント名を変更」。変更はヘッダーの表示にも即時反映する。ログインに使うユーザー名は変わらない旨を併記する。
- **パスワードの変更**: 現在のパスワード、新しいパスワード（12文字以上）、新しいパスワード（確認）を入力し「パスワードを変更」。12〜128文字・確認一致・現在と異なることを画面でも検証し、現在のパスワード誤りはサーバーのエラーを表示する。成功時は入力欄を空にする。

本人データCSVエクスポート、アカウント削除、全データ一括削除のボタンは初期リリースでは表示しない。

## 5. 共通UI状態とアクセシビリティ

- 各通信画面にローディング、成功、失敗、空状態を定義する。
- フォームにはラベル、説明、項目単位エラーを付ける。プレースホルダーだけで項目名を表現しない。
- フォーカス順を論理的にし、主要操作はキーボードで実行できる。
- 状態やチャートは色だけに依存せず、テキスト・数値・アイコン等を併用する。
- 削除など取り消しにくい操作は確認し、対象名を明示する。
- レスポンシブ表示で長いユーザー名、種目名、エラー文が重ならないことを確認する。
